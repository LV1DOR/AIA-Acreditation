## Behaviour and evidence

`POST /api/webhooks/resend` is a public Node route. It accepts at most 1 MB, including streamed requests without an accurate Content-Length. It decodes the original UTF-8 bytes and uses `resend.webhooks.verify` with `RESEND_WEBHOOK_SECRET`, preserving the SDK's signature/timestamp verification. It never parses and reserialises the body before verification. No sending API key is needed in the web process.

Subscribe to exactly:

```text
email.sent
email.delivered
email.delivery_delayed
email.bounced
email.failed
email.suppressed
email.complained
```

Verified supported events are committed in one serializable transaction: message correlation, event receipt, deterministic projection and reception heartbeat. `svix-id` has a unique constraint; duplicate receipts are harmless. A reused receipt ID with different signed bytes is rejected. Provider message/hash uniqueness handles concurrent first events. PostgreSQL serialization/deadlock conflicts use the project's bounded retry helper. An exhausted conflict or any failed write/commit returns 503; there is no background acknowledgement before persistence. Unsupported signed event types return 204 without storage.

HTTP responses: 204 stored/duplicate/unsupported/already-erased; 400 invalid signature, stale signature or malformed supported payload; 413 excessive body; 503 missing signing configuration or failed persistence. Persistence failure logs contain only a fixed diagnostic code and the validated webhook event ID. Never log raw payloads, signatures or SDK/DB errors.

The monitor retains sending state separately from provider observations. The summary uses conservative precedence: sent, delayed, delivered, failed, suppressed, bounced, complained. Later arrival cannot undo an observed adverse terminal outcome. All received observations remain in event-time order, with receipt time also shown. For contradictory terminal observations, the summary prioritises investigation; the timeline is the evidence. Equal-status observations select the later event timestamp deterministically. `deliveredAt` is the earliest actual delivered-event timestamp. A provider/API snapshot never creates delivery timestamps or fabricated historical events.

Correlation prefers the Resend UUID. `EmailProviderIdentity` preserves every provider UUID associated with a logical notification, including multiple existing SMTP attempts that reuse one RFC Message-ID. Every new event retains its own provider UUID. Search accepts any retained UUID; later events for an earlier UUID remain linked even without another RFC ID. For initial SMTP correlation, match the exact RFC Message-ID returned by the existing adapter against Resend's `message_id`. A webhook arriving before send acknowledgement is initially unlinked, then its events and identities attach transactionally to the queued record. Company, event and category stay on that original record. If the first event omits/rewrites the RFC ID, correlation is unavailable until matching metadata can be retrieved; never guess from recipient, subject or timing. Unlinked events have unconfirmed application origin.

There are no send, resend, retry, suppression-management, deletion or configuration controls in this feature. The only UI mutations are search/filter navigation. Existing unrelated operations are not exposed through Emails.

## Visibility and privacy

ADMIN users see complete recipient addresses, as explicitly requested. Search accepts recipient/address fragments, subject, company/event name, category or provider ID. It is case/accent insensitive and tolerates one insertion, deletion, substitution or adjacent transposition in terms of 4–48 characters. Shorter/longer terms match literal fragments. Multiple space-separated terms must all match; historical address hashes still support exact-address lookup. Lists use bidirectional keyset pagination (15 messages); timelines use keyset pagination (50 events). The status filter applies immediately; search applies after a 250 ms typing pause and resets pagination. There is no provider selector, Filter button or tracking-help disclosure. The read-only API retains its optional provider filter for operator compatibility. Dates display in Europe/Lisbon. The sidebar and both pages follow the existing Portuguese/English portal design.

Email bodies, invitation links and custom tags are not collected. ADMIN users can inspect the subject (998 characters maximum), sender and selected provider diagnostics: provider message (4,000 characters) and SMTP response (8,000 characters). Control characters and recognisable credential patterns are removed/redacted. Responses render as escaped text in expandable Technical details; plain bilingual explanations describe recipient-not-found and other failures. Existing encrypted sending payloads retain their current lifecycle.

New address metadata is subject to existing approved event/authentication policies. The redaction trigger clears addresses, all raw provider identities, RFC IDs, per-identity snapshots and event history. Non-reversible hashes of every known random provider/RFC ID remain as replay tombstones; they contain no recipient address and prevent late replays from restoring erased data. An unknown late UUID associated by a known erased RFC ID receives only a hash tombstone. Historical rows without recoverable provider/RFC IDs cannot be correlated after erasure. Unlinked events and external provider data require their own approved retention controls. No retention duration is invented here.

**Delivered means recipient-server acceptance, not guaranteed Inbox placement.** It says nothing about spam-folder placement or whether a person read the email. SMTP-only records show sending acceptance, with delivery unconfirmed. Clerk-managed invitation/authentication deliveries are not fetched or inferred. Resend events received from a shared team may belong to another application; unlinked origin must be investigated before attributing them to AIA. Use a dedicated appropriate Resend team/account where needed.

Historical recipient bodies/payloads are not decrypted or backfilled. Existing hashes can support exact-address search even when a full address was never retained; the page says the recipient was not recorded. Existing queue categories/scopes and known RFC IDs are backfilled conservatively by the migration. There is no promise of historical delivery completeness.

An authorised operator must create a webhook in Resend pointing to `https://<approved-app-host>/api/webhooks/resend`, select the seven events above, and provision its signing secret privately. This is a webhook setup only: do not change the sending domain, SMTP credentials or provider selection. Do not subscribe to opens/clicks for this feature.

Resend documents signature verification against raw bytes and SDK usage in [Verify Webhooks Requests](https://resend.com/docs/webhooks/verify-webhooks-requests), event semantics in [Event Types](https://resend.com/docs/webhooks/event-types), and SMTP integration in [SMTP](https://resend.com/docs/send-with-smtp). ## Failed webhook diagnosis

The ADMIN list API health result supplies the last successfully stored supported event, the last reconciliation observation, and Resend-labelled sends without a webhook after 15 minutes; these operator diagnostics are intentionally absent from the simplified Emails page. That 15-minute count is a diagnostic threshold, not an SLA or a declaration of delivery failure. No recent events may simply mean no sending activity. Messages sent through an unrecognised relay remain SMTP with visibility unavailable.

For missing events, inspect the endpoint in Resend's Webhooks dashboard: enabled state, destination, selected events, individual attempts, HTTP status and response. Compare its receipt ID with `RESEND_WEBHOOK_PERSISTENCE_FAILED` logs or the stored timeline ID. A 400 suggests wrong endpoint secret, altered body, stale signed timestamp or unsupported payload shape; verify UTC clock synchronisation without weakening verification. A 503 suggests missing signing configuration, database availability/grants, a failed commit or a conflict requiring retry. A 413 means the ingress/application limit was exceeded. Login/redirect/401/403 before the handler suggests an external authentication gate or wrong path.

Resend provides automatic webhook delivery retries and dashboard manual replays; repeated failures can disable an endpoint. After fixing the cause, an authorised Resend operator can re-enable/replay **webhook delivery**, which does not resend the email. No replay control is exposed in AIA. See [Retries and Replays](https://resend.com/docs/webhooks/retries-and-replays). The application cannot display provider delivery attempts that never reached it, so it does not claim an exhaustive failed-attempt history.

## Metadata reconciliation

Where the team's key permissions and API retention permit it, an operator can compare recently sent message metadata using the SDK's List Sent Emails endpoint. This command never sends emails, retries delivery, fetches bodies or changes Resend configuration. It updates local monitoring snapshots only for already-known matching IDs/RFC IDs. It does not import unrelated account messages.

```text
corepack pnpm exec tsx scripts/reconcile-resend.ts <explicit-target.json> <since-ISO-timestamp> [max-pages]
```

Inject `DATABASE_URL`, `DEPLOYMENT_ENV` and `RESEND_MONITOR_API_KEY` privately. The target JSON uses the existing `{environment,host,port,database}` format and must match the environment/database. Default limit: five pages of up to 100 messages; maximum: twenty pages. Output is counts and a `truncated` flag, never keys, recipients, bodies or provider error objects. Run again with a reviewed wider bound if truncated; do not assume the first pages are complete history. No reconciliation schedule is installed automatically.

Snapshots show when the API was queried and its reported status. They do not establish when delivery occurred and do not fabricate timeline events. A conservative terminal snapshot may elevate the summary while webhook evidence remains unchanged. If `last_event` is opened/clicked/queued/scheduled/cancelled, it is ignored rather than inferred as delivery; obtain the missing webhook history from Resend where available. Provider retention/key-permission limits can make historical reconciliation impossible. See [List Sent Emails](https://resend.com/docs/api-reference/emails/list-emails).

## Rollback

Prefer application rollback with the additive schema retained. Disable the new webhook endpoint in Resend if the candidate cannot persist events, then restore the prior immutable web/worker artifacts using the existing release procedure. Revert only the new optional configuration keys as part of that reviewed rollback; do not overwrite existing secrets. Existing SMTP/outbox code works with the expanded table; unlinked provider rows have no outbox relation and do not enter the worker queue. Keep the redaction trigger and history table so previously collected addresses still follow existing cleanup under an older worker.

Do not automatically run a destructive down migration or delete monitoring records. A later schema contraction requires a separate reviewed migration after the candidate is no longer running, with export/retention approval, backup and validation of unlinked rows; `outboxMessageId` cannot simply regain NOT NULL while such rows exist. If a transactional migration fails, inspect Prisma migration state and locks before retrying; never mark a failed production migration as applied without reconciliation.
