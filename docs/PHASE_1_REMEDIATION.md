# Phase 1: production security and data integrity remediation

Date: 12 October 2026, Europe/Lisbon. Baseline: the entire `PRE_PRODUCTION_AUDIT.md`, audited checkout `00ef9a7` including its existing user changes. This report concerns F01, F02, F03, F04, F05, F09 and F12 only. It does not certify production readiness.

## A. Summary

Implemented shared transactional worker/token restrictions, central company suspension, immutable photograph version keys and staged adoption, durable rejected-upload cleanup, current eligibility validation at leader/submission/final approval boundaries, and effective approval invalidation for relevant changes. Updated Sharp 0.35.4 → 0.35.5 and Next 16.3.6 → 16.3.8, with a targeted source-map-js 1.2.2 override. Preserved the workspace's existing Prisma-related security overrides. Unsupported image formats and mismatched MIME are rejected before native image decoding. Upload size, pixel, decoder concurrency and public request/key cardinality are bounded.

No production deployment, production migration, local operational-data migration, personnel editing, destructive reset or Volunteers change was performed. The additive migration was applied only through an explicit loopback:16432/`aia_acreditacao_test` guard. Tests use synthetic records and a dedicated `aia-phase1-synthetic` bucket. Existing user edits were retained. The normal PM2 web/worker processes were not restarted; their existing build/state is not evidence of the new release. The candidate Next build uses a separate ignored output directory.

## C. Technical changes

- `packages/domain/src/auth/authorization.ts`: company-active check for company leaders; admins keep authorised historical reads.
- `participants/service.ts`: transactional capability/state checks, obsolete token revocation, retired-worker guard; current eligibility on approval. A type-only identity change now requires the document number, preventing a stale fingerprint (directly related F19).
- New `participants/photo-lifecycle.ts`: durable staged upload creation, captured participant version, atomic adoption, abandoned-upload grace period and leased/retryable cleanup.
- `submissions/photo-adjustments.ts`: version-scoped originals read from the encrypted snapshot; optional original retrieval; append-only derivatives adopted with a checked adjustment generation.
- New `submissions/eligibility.ts`: actual required fields/encrypted identity completeness, birth date, normalised mobile, nationality, document validity through the event end, current active role, work dates, published event/company, active worker count, active requested event/global zones and vehicle request completeness.
- New `submissions/integrity.ts`: append approval invalidation for approved content, explicitly return an interrupted pending review, update current status/version, audit and notify/invalidate transactionally.
- `submissions/service.ts`: current eligibility on submit/approve; revoke outstanding employee links at submission; authorised invalidation/correction resubmission window.
- `events/service.ts`, `shared/catalogue.ts`, `companies/service.ts`, `companies/registration-service.ts`, `requests/service.ts`: apply the shared integrity contract. Reject below-count limits and inactive global zones. Catalogue sort-only changes do not trigger rereview.
- `admin/permanent-deletion.ts`: block deletion of submitted history or review/approved composition. Draft-only deletion remains supported. This closes the integrity/destruction path without disabling immutability triggers or pretending to implement F07/F08 erasure.
- `portal/queries.ts`: active-company direct leader participant reads; historical admin registration reads; participant version available to the server.
- `packages/storage/src/index.ts`: raster format/size/resource controls; `object-storage.ts` holds immutable conditional PUT and bounded PUT/delete requests. The worker imports the object-only entry point, without loading native image decoders, and declares its bundled external S3 dependency explicitly. Old/current accepted photograph objects are never deleted as part of upload replacement.
- Web participant, onboarding and AIA photo actions: authorised preflight → stage → process/store → guarded transaction; schedule abandonment on any failure. Overload feedback explains a retry in PT/EN without consuming the token. Back/Cancel saves only drafts, and safely navigates away from completed/correction records. Reopened approved workers can be edited; ordinary returned corrections can be resubmitted after deadline. These limited F10 repairs are necessary to preserve legitimate workflows, not a UI redesign.
- Historical photo GET accepts `?original=1` to retrieve source evidence; its normal response remains the latest derivative associated with that submission only.
- `proxy.ts` rejects declared POST bodies over 9 MiB with HTTP 413 before Clerk/route work. The streamed Server Action limit and external ingress remain required for omitted or deceptive Content-Length. `next.config.ts`, `server/rate-limit.ts`, new `server/public-request-policy.ts`, onboarding and invitation endpoints/actions: bounded request handling and secret-authenticated source policy. Client crop choices/help and PT/EN messages now agree with JPEG/PNG and 8MiB limits.
- Admin destructive action and PT/EN copy: explain protected historical deletion rather than generic failure.
- Worker: independent cleanup timer, scoped configured bucket, durable retries/crash lease recovery for staged objects. Cleanup outages do not block the existing mail/invalidation timer. Worker now requires the storage configuration and packages.
- Dependency manifests, `pnpm-workspace.yaml`, `pnpm-lock.yaml`: minimal production security updates. No indiscriminate dependency upgrade.
- New tests: `tests/unit/phase1-images.test.ts`, `phase1-public-policy.test.ts`, `tests/integration/phase1-security.test.ts`, `phase1-public-limits.test.ts`, and `tests/fixtures/security.ts`.
- Updated existing onboarding/submission/request/vehicle/browser fixtures to supply complete synthetic evidence. Existing assertions were retained. The old 150MiB assertion now checks the intentional 8MiB policy.
- `scripts/phase1-test-migrate.ts`, `scripts/benchmark-phase1-images.ts`, `scripts/smoke-phase1-worker.ts`, `.env.example`, this report and `docs/PHASE_1_INGRESS.md` document safe validation and deployment requirements.

## F. Remaining risks and policy decisions

F05 deployment acceptance remains incomplete: ingress controls, authenticated source headers, external app-port isolation, Linux native-image checks, aggregate multi-process memory limits and representative peak workload must be tested on the actual release environment. The required configuration and synthetic acceptance procedure are in `PHASE_1_INGRESS.md`; application controls alone do not bound memory already consumed by parsing many concurrent bodies.

Every effective accreditation amendment now requires new final review. This includes approved personnel-limit increases and configuration/name/role changes, even if an operator considers them harmless. AIA may later define traceable independently approved amendment categories; no such new business rule was invented. Existing independent vehicle pass decisions retain their explicit, audited separate outcome; they do not change the personnel/source request snapshot. AIA photo adjustments remain explicit append-only, submission-scoped review evidence.

Historical permanent deletion now fails closed and explains why. Draft-only erasure is still the existing process; durable all-copy erasure/retention, legal holds, backup expiry and immutability-trigger-compatible purge remain F07/F08, outside this implementation. F11's unsupported EDIT_PERSON/REPLACE_PHOTO and ADD_AFTER_DEADLINE completion workflow remain later work; unsuccessful decisions roll back, and successful existing mutation categories cannot retain misleading approval.

Old photographs already overwritten before this release cannot be recovered here. Old snapshots can preserve only the bytes currently at their stored legacy key. Raw object administration outside the app, compromised storage credentials or lifecycle rules can still delete/replace historical evidence; require scoped private storage privileges/backups. Conditional PUT is supported by the tested local MinIO; verify the deployed S3-compatible service. Enforce the same rule on every replica; mixed old/new writers must not run during release.

STAGED uploads expire after24 hours; rejected operations schedule cleanup after a five-minute grace exceeding the bounded PUT timeout. Cleanup leases retry every minute without a terminal attempt ceiling; only the configured accreditation bucket is eligible. Adopted objects/history are never swept by staged cleanup. CLEANED manifest rows remain for later retention policy. Worker availability is necessary for eventual cleanup, and outstanding manifests need operational monitoring in F18. Late writes beyond the bounded request/grace assumptions and externally created orphan objects require operational reconciliation; no cross-system atomic transaction is claimed.

The existing PostgreSQL adapter logs a pg concurrent-query deprecation warning in some tests; all tests pass. Mail terminal-lease recovery, backups, production identities/networking/privacy text and the remaining audit findings remain separate later phases. No end-to-end production delivery, production restore or complete PT/mobile/accessibility certification is claimed.

## G. Compatibility and migration

Events, companies, registrations, workers, encrypted submission snapshots, decisions and existing photo keys are retained. There is no destructive backfill. The new application never writes a deterministic legacy `profile.jpg`: historical retrieval decrypts each snapshot and uses that exact stored source reference. Existing legacy objects therefore become stable under new writers; subsequent edits adopt new UUID keys. This protects future history and freezes currently available legacy bytes, but cannot recreate earlier versions that shared overwritten bytes. Inventory/back up legacy objects and record uncertain historical evidence before operational use; do not rewrite immutable encrypted snapshots or claim lost bytes were restored.

Before any local operational restart or later authorised production release: back up DB/objects/required encryption keys; stop old photo writers; apply the additive migration through the reviewed migration role; regenerate/build/install the locked patched dependencies; configure private buckets, worker storage configuration and ingress controls; start only new-compatible web/worker artifacts; smoke-test with synthetic data. The local operational DB has **not** received this migration, so do not restart it on the new worker build until that deployment step is authorised and completed. Do not use a destructive reset or the local PM2 lifecycle as a substitute for a reviewed production release procedure.

Existing pending tokens are not bulk-modified by the migration. Server state guards deny obsolete/locked targets immediately. Legitimate pending links for active editable workers continue working; each later manual completion/submission/suspension revokes obsolete outstanding capabilities transactionally. Existing company memberships survive suspension/reactivation.
