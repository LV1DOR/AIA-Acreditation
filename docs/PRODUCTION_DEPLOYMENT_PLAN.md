# Controlled production deployment — preparation only

Prepared 15 October 2026. **Do not execute this plan during Phase 4A.** Actual VPS/provider inspection, DNS, production users, migration, restart and launch require explicit Phase 4B authorisation. No remote command was executed to prepare this document. Use the Compose route below; the older Phase 3 systemd release scripts are a separate alternative, not commands to mix into this release.

## Required inputs and stop conditions

The operator must record an approved host, architecture, domain, maintenance window, release/source hash, registry digests, storage-support decision, database identity, service UIDs, private paths, capacity budget, rollback images and configuration, and accountable technical/privacy/backup/incident functions. Missing inputs stop the deployment; no placeholder is an approved value.

The app images target **Linux amd64 / Node 22.23.3**, pinned by image digest, with pnpm 10.14.0 and the frozen repository lockfile. Recheck current support/advisories before building a real release. Node 22 is in the [official maintained release schedule](https://github.com/nodejs/Release); this is a bounded current runtime choice, not a permanent support guarantee. Build separately for the approved Clerk public key: Next embeds `NEXT_PUBLIC_*` at build time. A test-key image cannot become the production image by changing its environment.

The cached community MinIO release is **synthetic-only**. Its upstream is [archived and unmaintained](https://github.com/minio/minio). Production requires an approved supported compatible image/service and validation of its exact deployment/provisioning procedure. The supplied self-hosted Compose configuration expects the MinIO-compatible server command, certificate paths and API to be verified against that selection. An external S3 service needs a separately reviewed Compose dependency override; it is not silently assumed equivalent. This decision is a current production blocker.

Install the reviewed candidate source under `/opt/aia-accreditation/candidate`; configuration under `/etc/aia-accreditation`; backup data under `/var/lib/aia-accreditation/backups`. These are proposed accreditation-only paths to approve, not discovered VPS paths. The current checkout contains uncommitted Phase 1–4 changes: review and commit them or produce a verified source bundle containing the complete material inventory. **Do not use `git archive HEAD` and silently omit those changes.**

Create `/etc/aia-accreditation/compose.env` from `infra/production/compose.env.example`, and a complete release manifest from `release-manifest.example.json`. Every blank requires an actual approved value. The manifest records the exact environment/project/source/database/storage decision; images must use registry digests. Ports 18880/18443 are loopback proposals and must be changed consistently if occupied. Never publish backend ports to make a health check work.

Provision these files outside the repository/images:

| Path within the approved secrets/TLS directory | Requirement |
|---|---|

Worker has a different runtime login and optional separate erasure executor URL. `WORKER_HEALTH_HOST=0.0.0.0` is private-container-only; no host port. |

On Linux, use private parent directories and files owned/readable only by the intended service UID. Web/worker run as UID 1000; nginx as 101; Redis uses its image's `redis` UID. Confirm actual image UIDs before setting ownership. **Compose file-backed secrets retain host ownership**; declarations do not repair it. The Windows synthetic fixture's read-only shared-file permissions are not a production permission recipe. PostgreSQL briefly uses the official root entrypoint to prepare volume/key ownership, then drops to postgres; storage-volume-init changes ownership only on an empty dedicated volume and refuses incompatible existing ownership. The PostgreSQL Unix socket is trusted only inside that isolated container; it is not mounted into applications. All network connections require TLS/SCRAM.

## Operator command context

After authorisation, on the approved host only, use maintained Node/Corepack for the reviewed operator scripts and Docker Compose supporting health dependencies/resource limits. Supply the actual manifest/configuration paths; do not paste secrets into terminal commands or tickets.

```sh
set -eu
cd /opt/aia-accreditation/candidate
CFG=/etc/aia-accreditation/compose.env
MANIFEST=/etc/aia-accreditation/release-manifest.json
dc() { docker compose --env-file "$CFG" -f infra/production/compose.yaml "$@"; }
dc config --quiet
corepack pnpm exec tsx scripts/compose-preflight.ts "$MANIFEST"
```

Preflight is configuration/image/isolation validation, not availability, privacy approval or launch authorisation. It rejects remote Docker contexts, privileged web settings, public backend mappings, wrong targets, root application images, missing resource limits, mismatched image source labels and the known unsupported MinIO image in production.

Mounted secret-file content changes do not automatically recreate an existing Compose container. After an approved runtime configuration change, record the new protected-file fingerprint and use `dc up -d --no-deps --force-recreate web worker` for the affected services during the approved window. Recheck readiness before opening ingress. Merely editing the file and running `up` is insufficient; keep the previous protected configuration for reviewed recovery.

Host inspection must include working time synchronisation: inspect `timedatectl show -p NTPSynchronized -p TimeUSec` and the installed time service's status, compare container UTC and a trusted time source, and establish drift alerting. If unsynchronised, repair the approved host time service before Clerk acceptance; do not widen JWT tolerances or change provider security settings to conceal clock drift. The local Windows rehearsal found an unsynchronised CMOS source and Clerk about 50 seconds ahead. A separately approved elevated resync against the configured Windows source corrected the measured skew and signed-in testing resumed. Sustained host time-service health and actual VPS time synchronisation still need evidence.

Notification mutation CSRF checks use the validated `APP_ORIGIN` and explicitly approved additional origins, rather than an internal proxy route URL. Configure the exact public HTTPS origin; never populate it from arbitrary forwarded headers. Foreign/missing origins must return 403 without changing notification state. Production configuration restricts additional origins to the approved application origin.

## Backup and recovery limits

The coordinated backup's SHARE locks require an approved maintenance/schema-owner role; the SELECT-only `aia_backup` template role is **insufficient** for this adapter's lock/ledger operations. Local Linux evidence uses the isolated `aia_migrator` maintenance login. Do not grant ordinary web runtime these privileges or describe a write-capable maintenance login as read-only. Production must approve the least-privilege maintenance/custody arrangement or implement/rehearse a narrower privileged locking interface before launch.

Compose installations use the separately named `aia-accreditation-compose-backup.service/.timer` and `aia-accreditation-compose-monitor.service/.timer` templates, not the older host-process service units. Review paths, account, target and permissions before installing any unit. The `aia-release` operator account controls Docker and is effectively root-equivalent; it must be separate from application identities. Set an approved backup `OnCalendar` before enabling the backup timer; the template deliberately leaves it unset. Supply `BACKUP_APPROVED_EXPIRY` as an approved future timestamp, or `BACKUP_RETENTION_HOURS` plus `BACKUP_POLICY_REFERENCE` as explicitly approved values in the protected maintenance configuration. There is no default legal retention period. Reconcile event-specific cutoffs/holds with this archive policy before scheduling. Verify the first archive and an independent restore manually, then approve enabling the timer. Monitor templates require approved alert routing and a tested non-zero failure path before enabling; none has been installed in this phase.

The adapter rejects versioned/suspended source buckets. Unique immutable object keys support an approved new private unversioned bucket; no existing versioning is changed. Version-aware erasure removes old versions/markers, but that is not complete version-aware backup support. Retain and verify accessible external copies and expiry evidence. Actual production restore, standby activation, public-token paths and dispatch require separate acceptance; the current rehearsal helper deliberately refuses arbitrary/operational restore targets.

Do not run host-wide Docker cleanup, remove volumes, reset databases, disable history triggers, replay expired authentication tokens, blindly resend uncertain SMTP messages or roll schema backwards automatically. Keep service changes project-scoped. Use `docs/OPERATIONS_RUNBOOK.md` for detailed retention/erasure, message recovery and post-restore erasure reconciliation.
