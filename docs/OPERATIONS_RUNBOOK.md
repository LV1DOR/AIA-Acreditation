# Accreditation operations and recovery

These procedures prepare a future release. No production installation, VPS access, provider configuration or operational database migration has been performed. Use accreditation service names only. Do not alter Volunteers. Obtain the scheduled deployment authorisation before executing production commands.

## Configuration and startup

`DEPLOYMENT_ENV` is local, test, staging or production. `NODE_ENV=production` alone also describes a local build. Development/tests require explicit synthetic intent (`AIA_SYNTHETIC_DATA=true` or the guarded test environment). Synthetic notice/policy records are tagged and cannot enable production collection. Do not connect tests to the operational database.

Use `infra/production/environment.example` as a checklist, not a working environment file. It deliberately contains no credentials and unapproved control attestations. Provision three different operational keys and separate backup/custody keys through an approved secret manager. Web environment files must not contain migration, backup or privacy-executor credentials. Keep privileged worker/operator environment files separately readable only by the relevant service account. The application currently supports document/snapshot key version 1; retain the matching material with each backup. Do not rotate the active key while historical rows still require it without a separately reviewed migration/key-version plan.

Production requires live Clerk keys and signature verification; reviewed invite-only/session/domain settings; HTTPS public origin; authenticated TLS Redis; verified TLS SMTP sender and credentials; private TLS MinIO with scoped credentials; restricted TLS PostgreSQL runtime credentials; reviewed private ingress; distinct managed keys; approved privacy and backup configuration; and an explicit authentication-metadata policy cutoff/reference. Development TLS bypasses, testing tokens and debug settings are rejected. Attestations are operator prerequisites, not evidence that the VPS or providers have actually been configured correctly. Actual runtime-role checks reject schema owners, superusers, bypass/role-creation permissions and executor membership.

Provision the reviewed database roles before migrating. `aia_privacy_owner` is NOLOGIN and owns only the restricted functions; ordinary runtime credentials cannot execute them. Give the dedicated executor login membership in `aia_privacy_executor`, never to the web login. `infra/production/runtime-roles.sql` is a template requiring inspection on the actual target. Reapply grants after migrations/restoration. Verify private bucket policy, no public backing-service ports, TLS certificates, Redis isolation, filesystem encryption/permissions, webhook delivery and real sender delivery in the acceptance phase.

## Notices and retention

From administrator Overview choose **Privacy and recovery / Privacidade e recuperação**, then select the event. Publish AIA-approved Portuguese/English worker text and a separate responsible-person declaration, each with a distinct version and approval reference. `{event}` substitutes the selected event name. Publishing a new version does not change old text or acknowledgement evidence. Presented text, its SHA-256, locale, server version, actor and timestamp are retained. A changed version/hash requires the form to be refreshed. Production worker readiness also requires actual non-synthetic notice evidence; legacy checkbox fields alone are insufficient.

Record explicit approved dates for worker details, minimal decision evidence, event communications and backups. No legal retention periods are supplied. Dates become eligible at 00:00 UTC. Automatic destructive purging is disabled. Set/release a hold with an AIA reference when the approved process requires one. Missing/overdue policies are surfaced by monitoring. Account/provider retention and necessary fields, controller, lawful bases, notices, rights verification and legal holds remain AIA decisions.

## Erasure and copy reconciliation

Operational worker removal is distinct from privacy erasure. Empty draft cleanup is supported; personal or acknowledged/historical records require the privacy workflow. The implemented privacy scope is **all workers and historical versions in one company/event registration**, not deletion of a global company, Clerk account or every registration of a person. Review other events and provider/master records when handling a person-wide rights request. Do not describe a registration-scoped result as whole-person erasure.

1. Select the registration and **Personal data; retain approved minimal evidence**. Inspect counts, policy, date, holds and accessible backups. Refresh after any data/policy change.
2. Enter the actual AIA authorisation reference and confirm. The registration is frozen immediately; effective access stops. A queue acknowledgement is not completed erasure.
3. A privileged executor performs scoped database redaction. It removes identity ciphertext/fingerprint/phone/name/dates/references/tokens/work days/individual zones and acknowledgements; redacts encrypted snapshots, review comments, request content and audit metadata; preserves only the policy-authorised decision evidence/hash until its separate deadline. Immutability triggers remain active for ordinary callers. Historical UI shows the erasure marker rather than attempting to decrypt removed data.
4. The normal worker leases the durable object-deletion manifest, deletes each exact key including non-current versions/delete markers, and verifies absence. Outages remain retryable and visible. Object locks, missing permissions or remaining copies block verification. Pauses/holds must be reviewed; never force a row to VERIFIED in production.
5. Registered accessible backups keep the operation pending even after their expiry date. Use the archive deletion/verification routine for the explicitly managed destination, and separately verify every copied/off-site destination. Failed/partial backups also require reconciliation. Enter an external-copy verification reference only after actually checking processors, mailboxes/exports and other accessible copies under the approved procedure. Manual attestation is accountable evidence, not automatic provider verification.
6. The job becomes COMPLETE only after database redaction, all manifest objects, registered backups and the external-copy checkpoint are satisfied. Its label describes the selected scope. Minimal evidence still remains under its own policy.
7. After the approved evidence deadline, preview/confirm **Remaining evidence**. Complete copy reconciliation for that second stage. Request **Expire operation evidence** only once the registration/evidence and associated copies are gone; the restricted function then removes subject-linked operation receipts/manifests and retains an event-level SYSTEM action without worker/registration or actor identifiers.

If a queued database operation is blocked by a new policy or a disabled authorising administrator, inspect the actual reason/hold and renew authorisation under the latest approved policy. This does not silently bypass a changed date or hold. A storage outage needs repair/retry, not a new privacy policy. Do not globally disable triggers or use session settings to bypass protection.

Orphan discovery is an ADMIN-only domain API. It checks current photos, all decryptable snapshots, adjustments, staged grace periods and pending manifests. Confirm an event-specific policy and trustworthy ownership before queuing an orphan. Unknown legacy ownership or a missing historical key must be investigated rather than guessed. Orphan queuing rechecks historical/live references inside the transaction. Never use a blanket bucket deletion.

Event communications can be cleared after their approved date in the same screen. Global authentication delivery metadata requires `AUTH_METADATA_ERASE_BEFORE` and `AUTH_METADATA_POLICY_REFERENCE`; this selects completed/terminal records older than the approved cutoff, without deleting live credentials. It clears local recipient hashes/provider message IDs and payloads, not provider copies or account identities. Authentication payloads also have a five-minute technical send budget and are scrubbed on expiry; this is not a legal retention period.

## Coordinated encrypted backups

Choose RPO/RTO, cadence, retention and key custodians with AIA. None is guaranteed by this implementation. `scripts/backup.ts <target.json>` requires an explicit host/port/database/environment target, dedicated `BACKUP_DATABASE_URL`, private staging directory, approved expiry, destination, 32-byte binary backup and custody key files, and all three operational recovery keys. Use a restricted backup login. Native `pg_dump`/`pg_restore` and `tar` must be installed on Linux; the synthetic Windows rehearsal uses an identity-checked PostgreSQL Docker container.

The backup locks the business tables against concurrent writes while taking a custom PostgreSQL dump and immutable-object inventory, checks object-list stability, verifies that supplied keys decrypt documents/snapshots/pending encrypted mail, records migration checksums/configuration/key versions, then streams a tar archive through AES-256-GCM. Operational key material is in a **separate authenticated encrypted key bundle**, protected by an independent custody key, never plaintext in the database/object archive or source control. Ciphertext integrity is verified before a receipt is issued. A failed run remains visible; external service failure detection must also catch inability to reach the database. Use an approved maintenance window and private encrypted staging volume for real data.

The current backup adapter intentionally refuses versioned/suspended buckets rather than silently omitting old versions. The application uses unique immutable photo keys; use an approved unversioned private bucket for this adapter, or implement/test a complete version-aware backup adapter before enabling bucket versioning. Erasure does handle versioned objects and has been tested against real local MinIO.

`BackupRun.expiresAt` and the explicit approval are required, with no legal default. `deleteExpiredLocalBackup` checks the exact managed root and UUID filenames, removes archive/key bundle/receipt and verifies absence before recording DELETED. This does not discover arbitrary copies. Preserve the deletion journal and quarantine restores until the actual off-site/copy reconciliation procedure is approved. `offSiteVerified` remains false: no off-site destination has been configured or tested.

The backup systemd service/timer files are **uninstalled templates**. Fill an approved `OnCalendar` before enabling the backup timer. Do not copy plaintext secrets into unit files or ordinary archives. A timer without an approved calendar is intentionally not a functioning schedule.

## Restore and key recovery

Restore into a **new empty isolated database and a separate empty bucket**. Keep web, worker, SMTP and provider dispatch stopped. Verify encrypted archive/key-bundle checksums, recover the independent custody key, authenticate/decrypt before extraction, check safe archive members and object/database checksums, restore the matching schema, and reapply reviewed runtime/definer grants. Roles/passwords are not business-data backup contents. Never restore over the operational database.

The synthetic helper only permits loopback:16433/`aia_phase3_restore` and an `aia-phase3-restore-*` bucket. It retains a quarantine marker checked by authenticated actor resolution and web readiness. This marker is not network isolation or a blanket guard on every public token/worker path: keep web/public ingress and dispatch stopped throughout restoration. Review the **current authoritative erasure journal**, including operations performed after the selected backup, and reapply those erasures/copy reconciliation before making restored data accessible. A database backup cannot know erasures that happened later. Do not clear quarantine solely because the restore command exited zero. Full standby activation, including public-token and worker paths, requires separate acceptance.

Validate current and historical document decryption, notice evidence, review/snapshot consistency, original/adjusted photograph hashes and decoding, migration compatibility, role isolation, capacity/zones and worker/public-token restrictions. Check recovery keys against all retained versions, not only one sample. Restore should not replay old authentication codes; expired payloads are scrubbed and operator recovery forbids replay. Provider credentials, DNS/TLS/configuration and off-site custody recovery require separate real acceptance checks.

The local rehearsal evidence is in the Phase 3 report. Original/adjusted JPEGs, a historical snapshot and notice evidence were restored; wrong custody key/non-empty targets were rejected. The rehearsals preserve stopped synthetic containers as evidence; they are not production disaster recovery evidence.

## Releases and migration failures

`service:start`/`service:restart` on Windows now validate the exact local target, build/check isolated candidates before stopping PM2, require a verified scoped backup and compatibility review before migrating an existing schema, retain previous artifacts, then activate and check both readiness endpoints. They were not invoked against the operational stack here. The old running process is not stopped by a build/preflight/migration failure. Windows rollback preserves build artifacts; dependencies/configuration must also match them—do not assume an old build works with arbitrary changed dependencies.

`scripts/migrate.ts` rejects wrong deployment targets, failed migration history, arbitrary non-empty initial databases, non-additive schema changes needing expand/contract review, missing/failing backups and unreviewed old-artifact compatibility. `db:migrate` now uses this guard. The dedicated test migration helper remains exact loopback:16432/`aia_acreditacao_test`. No resets are used.

For Linux, package immutable candidate directories including source, locked dependencies, web/worker builds and a validation record. Keep secrets outside releases. `scripts/release.ts prepare` verifies candidate/target/backup/preflight without touching services. `promote` additionally requires an operator reference, atomically changes the accreditation current symlink and restarts only the two accreditation units. A failed health check returns to the known-good artifact. **It does not roll back the schema.** Only execute after inspecting compatible additive migrations and restoring the full matching artifact/configuration. Unit failure-injection tests cover sequence ordering and forward-recovery reporting; no real VPS cutover/rollback was executed.

If migration fails, leave running services untouched, inspect `_prisma_migrations` and the actual transaction outcome. Do not mark it applied/rolled back by assumption. In the isolated rehearsal one SQL syntax failure was confirmed fully rolled back, resolved as rolled back and corrected before reapplying. If activation fails after schema success, retain schema/data, restore compatible previous artifacts, and fix forward. Destructive changes require a separately reviewed expand/contract or clean-target restore process.

## Delivery failures and monitoring

The worker reconciles expired final-attempt leases as UNKNOWN, scrubs sensitive payloads and exposes the failure. Invalidation leases have the same recovery boundary. Terminal business messages retain only recipient/registration IDs for recovery; administrators may reissue a **fresh neutral portal update** after current role/membership/company/erasure checks. Old approval/deadline claims are not blindly replayed. Authentication and invitation failures require a fresh flow, never replay of an old token. Ordinary delivery also rechecks current recipient scope and neutralises stale submission-state copy. Stable Message-ID reduces some duplicates but SMTP cannot promise exactly-once delivery. An accepted send with lost acknowledgement is visibly uncertain.

Shutdown stops admission and waits up to 45 seconds for in-flight tasks before closing transports/database/Redis. PM2 uses the shutdown message and a 50-second timeout on Windows; Linux uses SIGTERM/TimeoutStopSec. A timeout exits non-zero and leaves leases for reconciliation. Actual local tests killed a claim process and held an SMTP send while requesting built-worker shutdown.

`scripts/monitor.ts <target.json>` emits counts/dependency availability/queue age/leases/backup age/failures/cleanup retries/retention reviews/current object bytes/disk space/repeated request errors, with no raw errors, addresses, tokens, images or identity data. Exit non-zero is the alert integration point. Configure web/worker origins, PostgreSQL/MinIO/backup volume paths and approved operational thresholds. Object counts are bounded and explicitly marked truncated; logical object bytes are not physical free capacity or old-version usage. Missing volume/provider monitoring is flagged. Next error instrumentation logs only REQUEST_FAILED and increments a bounded hourly Redis counter.

External alert routing, recipients, uptime monitoring, storage-volume/provider capacity, log rotation, service restarts and off-site freshness must be set up and tested by the acceptance team. The local monitor timer is a one-minute technical polling example, not an RPO guarantee. Public health routes expose generic dependency status only; operational details require ADMIN or the private CLI. Proxy access logs must omit URI/query strings containing bearer links and authentication tickets; the local Linux harness demonstrates a method/status/duration-only format.

If web/worker is unavailable: check the exact unit, readiness, PostgreSQL/Redis/MinIO, disk space and configuration; preserve data and record the failure. If delivery fails: repair provider/network/credentials, reconcile leases, inspect current recipient permissions, then choose a fresh valid flow/update. If backup is old/failed: stop release/migration, repair storage/custody/connectivity, take and verify a new coordinated backup, then rehearse restore. Never delete Docker volumes to repair connectivity.
