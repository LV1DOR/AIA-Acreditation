# Remove participation from one event

Admin-only, confirmed, version-checked and serializable actions replace the admin permanent-delete buttons. Removing a company records withdrawnAt on that one registration and closes it as REJECTED, removes its active people, revokes pending event invitations, cancels pending event requests, appends approval invalidation and an audit event, and queues a precise leader notification. Company identity and memberships are preserved for other events. Removing a person sets their existing status REMOVED, increments the registration version to prevent stale review, revokes only their pending links and cancels their pending requests. Colleagues retain approval. No deletes, object erasure, account disablement, secret changes or historical snapshot rewriting.

Active company/people views, event access, private photos, editing, requests, invitations, self-onboarding and effective accreditation enforce withdrawal. Admin Submissions continues to show the immutable registration history and labels the removed registration. Existing permanent-deletion/erasure APIs retain their original protections; this feature never calls them. A completed repeat returns without duplicate notifications. Cross-event IDs, changed versions, non-admins and active erasure jobs are rejected. No reinstate UI is introduced; reactivation needs a separately reviewed operation.

One additive transactional migration adds a nullable timestamp and a check constraint preventing a withdrawn registration from becoming approved through a stale action. Existing rows are unchanged. No new tables, roles or grants are introduced. The new column is backward compatible with the old images and is retained on code rollback. Database migration and application deployment require the operator's separate explicit confirmation after the PC tests/build/upload pass. Never reverse the migration or restore data automatically.

External gates: offline existing email/privacy/worker and new removal unit tests, all affected type checks with regenerated Prisma client, and a fresh network-isolated PC PostgreSQL with full schema migrations and real approved-history/other-event/idempotence tests. No VPS tests write data. Tests contain only synthetic fixtures, no email or app server. Actual new worker image must still render every email including both removal templates before export. All three immutable application images advance under the existing matching-material release model. Backup and quiesce writers before the additive migration, preserve dependencies/Nginx and take rollback bindings. Manual fresh encrypted backup off-VPS copy remains required.
