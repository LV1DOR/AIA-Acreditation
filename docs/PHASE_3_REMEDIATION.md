## Data inventory and scope

Worker rows contain encrypted identities and plaintext operational fields; work days/zones/tokens/references accompany them. Encrypted submission snapshots duplicate those fields and refer to immutable originals/adjustments. Review/request comments and audit reasons can contain personal content. Acknowledgement records hold presented notice text and actor references. Notifications, outbox/auth payloads, delivery recipient hashes/provider IDs, import batch hashes and backup copies require separate lifecycle treatment.

Registration privacy preview discovers current/retired workers, all submission versions, adjustments, staged/adopted manifests and notice evidence. The database step clears those worker details, redacts snapshot/comment/request content and removes tokens/work days/individual zones/import records. Current and historical photograph keys feed the durable deletion manifest. Normal clients cannot mutate history, and an erasure tombstone/guard continues to prohibit resurrection even after operation evidence expires.

The scope is workers/history **inside the selected registration**. Company masters, Clerk/admin/leader identities, another event's legitimately retained record, provider mailboxes/exports and unregistered backup destinations are not automatically erased. Operator verification must cover relevant copies and a wider rights request must locate/review those other scopes. Avoid claiming a whole person's erasure from one registration result. AIA must approve account/audit/processor retention and rights verification. Event communication purge and explicit global auth metadata cutoff support local records; external copies require accountable verification. Raw spreadsheets are not retained by the application; synthetic import tests still require incomplete photos/acknowledgement rather than invented defaults.

A backup expiry date alone never counts as deletion. Existing/failed/partial registered backups block completion until their exact managed copies are removed/verified. The manual external-copy reference is an operator attestation, not an automated provider API proof. Minimal decision evidence and operation receipts have separate approved expiry and are discoverable for restricted cleanup. Automatic destructive purging stays disabled.

## Schema and migrations

Five additive migrations were applied only to the identity-guarded `127.0.0.1:16432/aia_acreditacao_test`, and to newly created synthetic restore-source databases on port 16433:

1. `20261014000100_privacy_recovery`: notice/acknowledgement/policy/hold/erasure/storage-deletion/backup/heartbeat tables, nullable erasure markers and outbox scope/recovery/terminal metadata, restricted definer functions and immutability/scope guards.
2. `20261014000200_privacy_scope_reconciliation`: bounded audit redaction exception, unambiguous legacy message scope linking and latest-policy/event-scope checks.
3. `20261014000300_privacy_configuration_classification`: synthetic classification defaults fail closed for old notice/policy/job records; server-controlled publication sets the actual classification.
4. `20261014000400_erasure_evidence_expiry`: authorised operation-receipt expiry, durable tombstone protection and restricted receipt purge.
5. `20261014000500_privacy_executor_backup_lookup`: SELECT-only copy-status lookup for the evidence-expiry definer.

No original data was dropped, existing history globally unlocked or migration rolled back by destructive reset. An early syntax failure in the first migration was confirmed completely rolled back in the isolated test database, marked rolled back, corrected and reapplied before any successful application; subsequently applied migrations were extended through additional migrations rather than rewritten.

The NOLOGIN database roles are database privileges, not new application roles. ADMIN and COMPANY_LEADER remain the only application roles. The normal web login is not an executor or schema owner. Restricted functions fix their search path and revoke PUBLIC execution following [PostgreSQL's SECURITY DEFINER guidance](https://www.postgresql.org/docs/17/sql-createfunction.html). Object erasure removes non-current versions/delete markers rather than relying on a marker-only delete; [S3 documents why a normal versioned DELETE does not erase those copies](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html).
