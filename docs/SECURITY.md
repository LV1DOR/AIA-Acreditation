# Security

There is no unauthenticated development admin shortcut. Clerk sessions are verified by the current Next.js SDK middleware, while every protected page and domain query enforces access again next to the resource.
Role and membership authority lives in PostgreSQL. Client-supplied identity or role claims must never become ActorContext.
Runtime environment errors are generic, with no original values. Logs accept fixed codes and UUID context only; request bodies, URLs, raw errors and PII are not passed through.

The portal fails closed when any required Clerk value is missing or malformed. Liveness remains available, but web readiness returns HTTP 503 with only the unavailable dependency name. Admin access requires an individually verified Clerk account mapped to the PostgreSQL `ADMIN` role by the controlled bootstrap command. MFA is not required because it is unavailable on the selected Clerk plan. Company leaders receive no role or company membership from Clerk metadata or public sign-up. PostgreSQL membership is created only by consuming an AIA-issued invitation.

Direct Clerk account creation is not exposed. The sign-up component requires both a still-valid hashed AIA invitation represented by an HttpOnly cookie and a Clerk application-invitation ticket. That non-emailing Clerk ticket is created server-side only after the recipient opens the AIA link and chooses to create an invited account; existing recipients sign in instead. A Clerk account alone grants no portal role or company membership, and an internal administrator identity cannot consume a company-leader invitation.

Leader invitation tokens contain 256 random bits, are stored only as SHA-256 hashes, expire, may be revoked and are consumed once using a serializable transaction. Acceptance requires a verified Clerk email matching the normalized invited address. Raw tokens are removed from the URL into a Secure/HttpOnly/SameSite cookie, are never written to audit metadata, and invalid/expired/revoked/used invitations share one public response.
Invitation emails are created only inside the authorised invitation transaction. The raw token exists at rest only inside an AES-256-GCM encrypted outbox payload, which is scrubbed after delivery. The administrator UI never renders or logs it.

Phase 3 Server Actions re-check the required portal role. Domain services then re-resolve the database user and company membership inside the serializable transaction. Registration detail queries are membership-scoped; an unowned registration identifier is returned as not found. Company leaders cannot create companies, registrations, memberships or invitations, and cannot set personnel limits or approval fields.

Phase 4 worker records are event-specific. Employee links contain 256 random bits, store only a SHA-256 hash, expire no later than onboarding close, may be revoked while unused, and are consumed once in the same serializable transaction as the worker update. Employees do not receive accounts. Public view and submit routes are rate-limited through Redis using a hash of the token, so the raw token is not used as a cache key.

Phase 5 submission snapshots are encrypted with AES-256-GCM before persistence using the already validated document-encryption key and a submission-specific authenticated-data context. The plaintext canonical snapshot is used only in memory to derive its SHA-256 integrity hash and encrypted envelope. Snapshot rows and their separate review rows have database triggers rejecting update and delete. Leader projections receive submission metadata and review feedback but not decrypted snapshot payloads; only an authenticated administrator review query decrypts the selected snapshot. Snapshot contents and free-form review comments are never copied into audit metadata or invalidation messages.

Document numbers are normalised only in memory, encrypted with AES-256-GCM using the participant ID as authenticated data, and separately fingerprinted with HMAC-SHA-256 over document type plus normalised number. The encryption and fingerprint keys must be distinct. PostgreSQL stores the encrypted value, keyed fingerprint, and last three normalised characters. After an active company-membership query succeeds, the server may decrypt that company's participant number for the authorised leader's operational verification; projections still explicitly discard ciphertext, IV, authentication tag, fingerprint and key version. Cross-company data remains inaccessible. Only an administrator can see the company-level context of a same-event duplicate; leaders receive a generic review message. Audit metadata, logs and outbox messages never contain document, phone, photo, name or raw-token values.

Photos are accepted only through authenticated leader actions or a valid one-time employee link. The browser requires a square crop confirmation and offers pan, zoom and 90-degree rotation before it attaches a bounded 1200x1200 JPEG to either form. Existing private photos can be fetched through the authorised endpoint and reframed by a leader. Source files are limited to 150 MiB at the browser, Server Action boundary and storage pipeline before buffer allocation. Sharp remains authoritative: it separately limits decoded input to 30 million pixels, validates the decoded image, applies orientation, strips metadata through re-encoding, constrains the long edge to 1200 pixels and writes only the processed JPEG to a private MinIO bucket. Optional ClamAV scanning occurs before image processing and fails closed. Photo retrieval uses an authenticated, company-authorised endpoint with private/no-store caching; object keys are not public URLs.

During a pending AIA review, an administrator may create a new square framing for a submitted worker photo. This writes a versioned private object and an append-only `SubmissionPhotoAdjustment` tied to that exact submission and participant; it never overwrites the company workspace photo or alters the encrypted submission snapshot. The admin photo route rechecks the database ADMIN role, exposes only the latest derivative for that submission, and uses private/no-store caching. Once the submission is decided, the adjustment control and mutation are unavailable. Each adjustment is audited without copying photo data or object keys into audit metadata.

The public Clerk webhook endpoint accepts at most 1,000,000 bytes and calls Clerk's `verifyWebhook()` before using any event data. Only undelivered `email.created` events are accepted into the outbox. Recipient and message bodies are encrypted with AES-256-GCM until the worker sends them through the SMTP adapter; successful and terminally failed payloads are scrubbed. Webhook retries are deduplicated by a hash of the Clerk email event ID.

Audit metadata is schema-validated and allowlisted. Free-form vehicle justification lives in the business row, not audit/log metadata. Phase 3 create/update/configure/invite/revoke actions append audit records and durable invalidations in the same transaction.
Outbox invalidations contain entity IDs and versions only.
Current append-only audit triggers prevent ordinary UPDATE/DELETE, not database-owner tampering. Production needs separate migration/runtime roles and restricted grants.

SMTP credentials are environment-only. Remote SMTP requires TLS (implicit or STARTTLS), certificate verification is not disabled, and Nodemailer logging/file/URL access are disabled.
Email transport errors discard provider text. Real messages and recipients must not enter test fixtures.
Stable Message-ID is useful for correlation but SMTP does not guarantee exactly-once delivery. Future delivery/outbox processing must explicitly handle the crash-after-acceptance ambiguity.

Before exports: version referenced photo objects, authorise decryption and use short-lived private downloads. Submission snapshots are encrypted, but the final retention policy must still cover every snapshot copy.
Before destructive retention: approved purpose/timing, all PII copies tracked and legal holds checked.
Before production: live Clerk production-instance verification, TLS/CSP, dedicated DB role and storage credentials, restricted networks, off-site encrypted backup and restore evidence.

No production secret is included. .env.example contains only explicit local development credentials and placeholders for independently generated document keys. Local MinIO credentials and local-only keys in an ignored `.env` must never be reused outside this workstation.

Prisma CLI is a development dependency. The lockfile overrides its transitive deepmerge-ts to 8.0.2 and mysql2 to 3.24.4 to address reported advisories; this app uses PostgreSQL, not MySQL. Reassess these overrides when updating stable Prisma. Validate/generate/migrate and the full suite must pass with these resolutions.
